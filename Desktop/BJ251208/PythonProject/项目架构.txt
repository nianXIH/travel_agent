一、技术选型
------------------------------------------------------------
Web 框架      : FastAPI + Uvicorn
流式输出      : SSE（sse-starlette）
Agent 编排    : LangGraph + LangChain Core
LLM           : 阿里云百炼 qwen3.8-flash（OpenAI 兼容接口）
Embedding     : BGE-m3（本地 FlagEmbedding，1024 维 dense + sparse）
向量数据库    : Milvus 3.0.3 standalone（Docker Compose）
重排序        : bge-reranker-v2-m3（建议启用，可开关）
历史对话存储  : MongoDB（pymongo 异步客户端，不使用已废弃的 motor）
导入任务      : 自建 IngestionWorker（asyncio 串行队列）+ MongoDB 任务表
配置管理      : pydantic-settings + .env
日志          : loguru
文档解析      : Markdown/TXT 原生解析；PDF 用 pypdf；DOCX 用 python-docx
管理后台      : 原生 HTML/CSS/JS（StaticFiles 挂载 /admin，无构建步骤）
用户端        : 原生 HTML/CSS/JS（StaticFiles 挂载 /app，无构建步骤）

四、分层职责
------------------------------------------------------------
API 层（app/api）
  只负责请求校验、参数注入、响应组装、SSE 转发；
  不直接访问 Mongo/Milvus，不包含业务规则。

应用编排层（app/ingestion、app/retrieval、app/chat）
  实现导入、检索、问答三条业务链路；
  调用仓储与模型基础设施，处理降级与重试。

领域模型层（app/schemas）
  Pydantic 模型，定义请求/响应、内容元数据、引用、SSE 事件。

基础设施层（app/repositories、app/retrieval 内的客户端、app/core）
  MongoDB、Milvus、Embedding、Reranker、LLM、配置、日志。

依赖方向：api -> 应用编排 -> 基础设施；禁止反向依赖。


五、核心链路
------------------------------------------------------------
1. 文档导入

   POST /api/v1/ingest/scan 或 /upload
        |
        v
   上传校验（仅 upload）：后缀白名单、MAX_UPLOAD_MB、
   空文件拒绝、文件名取 basename、重名追加序号，
   保存到 数据/uploads/
        |
        v
   扫描目录（scan）：遍历支持的 md/markdown/txt/pdf/docx
        |
        v
   创建 MongoDB 导入任务（queued）并提交 IngestionWorker
        |
        v
   Worker 串行执行（Semaphore(1)，避免并发占用显存），
   状态流转 queued -> running -> success / partial / failed / cancelled
        |
        v
   逐文件：计算 sha256 -> 与 documents 表比对（增量/幂等）
        |
        v
   加载文本（md/txt 直读；pdf 用 pypdf；docx 用 python-docx，
   标题样式转 Markdown 标题，表格转文本）
        |
        v
   解析“## 元数据” + 目录映射内容类型
        |
        v
   按 H2/H3 标题路径切块（约 600-800 中文字，重叠 80）
        |
        v
   BGE-m3 批量编码 dense + sparse（与问答共用 GPU 锁）
        |
        v
   按 doc_id 删除旧块 -> Milvus 插入新块 -> flush
        |
        v
   更新 documents、ingestion_tasks（每文件计数/当前文件/errors）

   规则：
   - 单文件 try/except，失败不影响其他文件；全部失败为 failed，
     部分失败为 partial；
   - 任务记录成功数、失败数、当前文件、错误详情、起止时间；
   - 重试：POST /ingest/tasks/{task_id}/retry，校验任务已结束、
     存在失败文件、源文件仍在数据目录内（防路径穿越），
     以新任务 task_type=retry、force=True 重新执行；
     任务运行中返回 409，无可重试文件返回 400；
   - 服务关闭时 worker 停止接收新任务，取消未开始任务并标记 cancelled；
   - 目录到内容类型映射：
       景点攻略 -> 景点介绍
       线路推荐 -> 线路推荐
       酒店信息 -> 酒店信息
       美食推荐 -> 美食推荐
       交通指南 -> 交通指南
       文化民俗 -> 文化民俗（后续扩展）
   - ENRICH_WITH_LLM=true 时，用 LLM 补全缺失字段；默认关闭。
   - 增量同步与删除清理（CLI --prune / scan.prune=true）：
       扫描结果与 documents 表比对；sha256 未变且 status=imported 时跳过；
       源文件已消失的文档标记 status=deleted、chunk_count=0，并按 doc_id
       删除 Milvus 旧块，保留文档行用于审计；
       重命名视为“旧路径删除 + 新路径导入”；
       重复导入幂等（内容未变跳过；force=true 按同一 doc_id 覆盖，不重复建块）；
   - prune 安全约束：只允许对 DATA_DIR 执行完整扫描后清理——
       拒绝与 limit 组合、拒绝空扫描、拒绝任务文件集与 DATA_DIR 重扫不一致
       （防止只传部分文件时误删全库）；--dry-run 仅列出待清理文件，不写库。

2. 三路检索

   用户查询 + 会话历史
        |
        v
   LLM 查询改写 + 意图/过滤条件抽取（城市、内容类型、景点名等）
        |
        +---------------------------+---------------------------+
        v                           v                           v
   路径 A：hybrid              路径 B：HyDE                路径 C：Web
   Milvus dense+sparse         LLM 生成假设文档            search_pro MCP
   各 top20，RRF(k=60)          BGE-m3 编码后向量检索       联网检索 top5
        |                           |                           |
        +---------------------------+                           |
                    |                                           |
                    v                                           |
   本地 RRF（hybrid=1.0，hyde=HYDE_WEIGHT=0.9）                 |
                    |                                           |
                    v                                           |
   bge-reranker-v2-m3 针对原始 query 重排，取 top5               |
   （失败降级为本地 RRF 顺序）                                  |
                    |                                           |
                    +---------------------+---------------------+
                                          |
                                          v
              最终 RRF（local=1.0，web=WEB_SEARCH_WEIGHT=0.7）
              - web 最多 WEB_SEARCH_MAX_CITATIONS=2 条
              - 本地有结果时至少保留 WEB_SEARCH_MIN_CITATIONS=1 条 web
              - 去重键：知识库 chunk_id / 网页 URL 哈希
                                          |
                                          v
                              返回片段 + 引用信息

   并发与资源：hybrid 与 HyDE 生成并行；HyDE 向量检索在 hybrid 完成后执行，
   避免本地 embedding 并发争用显存；web 检索全程独立并行。
   降级策略：任一路失败只标记该路 status 并加入 degraded，不影响其余路径；
   全部本地路径失败且 web 为空时返回无上下文答案。
   路径状态：ok / empty / disabled / unavailable / error，附 hits 与 elapsed_ms。

   引用字段：chunk_id、city、content_type、scenic_name、route_name、
             source_file、source_path、section_path、score、rerank_score、
             source_type(kb/web)、title、url、site、published_at、
             retrieval_sources(hybrid/hyde/web)、fusion_score

   评测（scripts/eval_retrieval.py）：
   - 30 条黄金问题，按 source_file 命中位置计算 Hit@1/3/5 与 MRR；
   - --pipeline local：dense / sparse / hybrid / hybrid+rerank 对比；
   - --pipeline three-way：最终融合结果评测，并输出各路径状态、
     降级次数、web_in_final 与平均耗时；
   - --routing heuristic：复用生产启发式路由，将城市/内容类型
     作为过滤条件（与问答链路一致）；
   - --show-hits N：输出每条查询的最终命中来源，便于定位错排；
   - --limit N 可先跑子集；退出码在 Hit@top_k < 0.9 时为 1。
   - GPU 单卡环境下运行前需先停止服务，避免模型显存冲突。
   - 基线（2026-10-24，30 条，top_k=5）：
       无路由过滤 : Hit@1=0.833 Hit@3=1.000 MRR=0.911
       启发式路由 : Hit@1=1.000 Hit@3=1.000 MRR=1.000

3. 问答（LangGraph）

   load_history
        |
        v
   rewrite_and_route      结合历史改写，判断意图与过滤条件
        |
        v
   retrieve               三路检索 + 两阶段融合（重排在此节点内完成）
        |
        v

        |
        v

   流式事件（SSE）：
     event: stage   {stage: "retrieving" | "web_searching" | "hyde_generating"
                          | "reranking" | "fusing" | "generating"}
     event: meta    {session_id, message_id, rewritten_query, intent,
                     citations: [...], retrieval: {hybrid, hyde, web,
                     fusion, degraded, elapsed_ms}}
     event: delta   {content: "..."}
     event: done    {finish_reason, elapsed_ms, usage}
     event: error   {code, message}

   历史策略：
   - 读取最近 CHAT_HISTORY_MAX_MESSAGES 条消息；
   - 消息数超过 CHAT_SUMMARY_TRIGGER 时异步更新会话摘要；
   - 第一版不使用官方 checkpointer，自管会话与消息集合。

4. 行程规划与智能推荐（/itineraries、/recommendations）

   请求解析（目的地、天数、人数/人群、预算、兴趣、节奏、住宿偏好）
        |
        v
   分类知识检索（RetrievalService：hybrid + rerank，按内容类型过滤）
   - 行程：景点介绍 / 线路推荐 / 酒店信息 / 美食介绍 / 交通指南
   - 推荐：景点 / 美食 / 酒店 / 线路（综合 = 景点 + 美食 + 酒店）
        |
        v
   引用去重与全局编号（1..N，最多 PLANNER_MAX_CITATIONS=12）
        |
        v
   LLM 结构化生成（JSON，PLANNER_TEMPERATURE / PLANNER_MAX_TOKENS）
        |
        v
   Pydantic 校验 + 引用编号清洗（越界/重复丢弃）
        |
        v
   返回逐日行程或推荐项 + 引用 + 分类检索状态 + token usage

   - 与问答链路一致，只允许引用知识库资料，不编造名称与价格；
   - 目的地支持城市名与别名（如昆明→云南、鼓浪屿→厦门），未命中城市时
     退化为不带城市过滤的全文检索；
   - 无知识库结果返回 404 NO_CONTEXT 且不调用 LLM；
   - 单个内容类型检索失败只标记 status=error 并计入 degraded，其余类型继续；
   - LLM 未配置 503；调用失败 502 UPSTREAM_ERROR；JSON 非法或字段不合法
     502 INVALID_LLM_OUTPUT；
   - 引用条目字段与问答一致，`sources` 为资料编号（从 1 开始）；
   - 规划链路无状态，不写入会话与任务集合。

5. 管理后台（/admin）

   静态页（StaticFiles，html=True）→ 原生 JS 调用 /api/v1
   - 概览：文档/任务按状态聚合、城市与类型分布、Milvus 分块总数；
     Milvus 不可用时 chunks=null + chunk_error，接口本身仍返回 200；
   - 知识文档：keyword/status/city/content_type 过滤与分页；详情附
     Milvus 分块预览（按 chunk_index 排序，最多 200 条）；
   - 导入任务：状态过滤、分页、失败任务重试；
   - 上传与扫描：复用 /ingest/upload 与 /ingest/scan（强制扫描二次确认）；
     prune 仍建议使用 CLI 并先 --dry-run；
   - 检索测试：调用 /search，展示模式、耗时、重排状态与引用；
   - Tab 使用 URL hash（#documents/#tasks/...）深链，刷新保持当前位置；
   - ADMIN_TOKEN 非空时 /api/v1/admin/* 要求 X-Admin-Token，页面保存在
     sessionStorage；为空时不校验（仅建议内网使用，后续由权限/多租户接管）；
   - 管理 API 只读，写操作仍走既有导入、上传与任务重试接口。

6. 用户端（/app）

   面向旅行者的单页应用（StaticFiles，html=True）→ 原生 JS 调用 /api/v1
   - 凭证门禁：输入 API Key 后调用 GET /catalog 校验；凭证只写入
     sessionStorage，关闭标签页即清除；页面不引用任何管理令牌；
   - 问答：POST /chat/stream 读取 SSE（stage/meta/delta/done/error），
     展示阶段、意图、流式正文与引用来源；支持停止生成与新对话；
   - 检索：POST /search，展示相关度、城市/类型/章节与原文链接；
   - 行程：POST /itineraries，逐日展示时段、餐饮、住宿、预算与提示；
   - 推荐：POST /recommendations，按类别展示推荐项、亮点与适用人群；
   - 渲染统一使用 DOM textContent，不拼接服务端/模型返回的 HTML；
     401 自动回到凭证门禁，其余错误显示中文提示；
   - 同一标签页更换凭证时清空上一凭证的会话与结果，避免跨租户残留。

7. 问答质量评测（scripts/eval_qa.py）

   - 数据集：qa_cases.json，每条含 id、question、expected_sources、
     expected_facts；
   - 链路复用生产检索（RetrievalService + ThreeWayRetriever）与
     ChatLLM 生成，不经过 ChatService，避免写入 Mongo 会话；
   - 指标：
       citation_hit     期望来源是否至少被引用一条（0/1）
       citation_recall  期望来源的引用覆盖率
       fact_coverage    期望事实在答案中的覆盖率（忽略空白/大小写）
       judge_score      可选 LLM 评审（1-5 分 + 理由，--judge 开启）
       latency / answer_chars 平均耗时与答案长度
   - CLI：--cases --limit --top-k --routing off|heuristic --judge
          --json-out --min-citation-hit 0.9 --min-fact-coverage 0.8；
     单条失败不中断整轮，计入 failed；阈值不满足时退出码为 1。
   - GPU 单卡环境下运行前需先停止服务，避免模型显存冲突。
   - 基线（2026-10-24，12 条，top_k=5，启发式路由）：
       citation_hit=1.000 citation_recall=1.000 fact_coverage=0.924
       avg_latency_ms=11801 avg_answer_chars=587
     未覆盖事实：城市便利（答案写作“交通便利”）、轮渡、玉龙雪山。


六、数据模型
------------------------------------------------------------
1. MongoDB（数据库：travel_kb）

   documents
     _id, tenant_id, doc_id, source_path, source_file, sha256, content_type,
     city, status(imported/failed/deleted), size, mtime, chunk_count,
     imported_at, deleted_at, error

   ingestion_tasks
     _id, tenant_id, task_type(scan/upload/retry), status(queued/running/
     success/partial/failed/cancelled), total, succeeded, failed, skipped,
     pruned, prune_failed, current_file, errors[],
     created_at, started_at, finished_at

   chat_sessions
     _id, tenant_id, user_id(可空), title, summary, message_count,
     created_at, updated_at

   chat_messages
     _id, tenant_id, session_id, role(user/assistant), content, citations[],
     intent, token_usage, created_at

   索引：
     documents: uq_doc_id(doc_id)、uq_tenant_source(tenant_id+source_path)、
                ix_tenant_sha256、ix_tenant_city_type、ix_tenant_status_imported
     ingestion_tasks: ix_tenant_status_created、ix_tenant_created
     chat_sessions: ix_tenant_user_updated、ix_tenant_updated
     chat_messages: ix_tenant_session_created
     说明：所有查询必须先带 tenant_id；跨租户资源统一返回 404。

2. Milvus（collection：travel_chunks）

   字段：
     chunk_id         VARCHAR  主键，格式 "{doc_id}:{chunk_index}"
     tenant_id        VARCHAR  租户标识（必填，所有查询/写入强制过滤）
     doc_id           VARCHAR
     content          VARCHAR
     content_type     VARCHAR
     city             VARCHAR
     scenic_name      VARCHAR
     route_name       VARCHAR
     hotel_name       VARCHAR
     restaurant_name  VARCHAR
     source_file      VARCHAR
     source_path      VARCHAR
     section_path     VARCHAR
     chunk_index      INT64
     extra            JSON     行程天数、预算、tips 等非固定字段
     updated_at       INT64
     dense_vector     FLOAT_VECTOR(1024)
     sparse_vector    SPARSE_FLOAT_VECTOR

   索引：
     dense_vector  : HNSW + COSINE
     sparse_vector : SPARSE_INVERTED_INDEX + IP
     tenant_id     : INVERTED（租户过滤）
     融合策略      : RRFRanker(k=60)
     一致性级别    : Strong（数据量小，优先正确性）

   说明：
     - 不启用分区，先使用元数据过滤；数据量增大后再按 city 做 partition key；
     - 过滤表达式中的用户输入必须转义，避免表达式注入；
     - 单 collection + tenant_id，禁止无租户条件的检索、删除与计数。

十、关键风险与约束
------------------------------------------------------------
1. Windows 不支持 milvus-lite，必须使用 Docker 部署 Milvus。
2. RTX 5070 Laptop 为 Blackwell 架构，torch 必须为 cu128 及以上版本。
3. 8GB 显存同时容纳 BGE-m3 与 reranker（fp16 约 4.5GB），
   批大小控制在 8 左右，禁止多 worker。
4. 本地 embedding 为同步阻塞调用，必须放入线程池，避免阻塞事件循环。
5. 阿里云百炼负责问答生成，不承担 embedding；向量化完全由本地 BGE-m3 承担。
6. LangChain 生态版本迭代快，首次跑通后使用 pip freeze 锁定版本。
7. 检索过滤表达式需转义；上传接口需做后缀白名单与大小限制。
8. 流式回答过程中客户端断连时，仍需保存已生成的部分内容并标记状态。

十三、权限与多租户（2026-10-25，已完成）
------------------------------------------------------------
1. 租户来源与开放模式
   - 租户为环境变量静态配置：TENANTS=[{tenant_id, tenant_name, api_key,
     role}]；tenant_id 校验 ^[a-z0-9][a-z0-9_-]{0,63}$。
   - default 租户始终存在；TENANTS 为空时为开放模式：匿名请求按
     default 租户 admin 处理，便于本地开发；若同时设置 ADMIN_TOKEN，
     /admin/* 仍要求 X-Admin-Token。
   - 启动时校验：api_key 至少 16 字符、互不重复；ADMIN_TOKEN 必须与
     所有 api_key 不同；tenant_id 重名时 tenant_name 必须一致。

2. 认证与角色
   - X-API-Key → 租户凭证；X-Admin-Token → 全局管理员；
     X-Tenant-Id → 目标租户（全局管理员用于跨租户，租户凭证只能等于自身）。
   - 角色等级 viewer < editor < admin：
       viewer  检索、目录、问答、SSE、会话、规划、任务查询
       editor  扫描、上传、任务重试
       admin   管理 API 与后台页面；全局管理员可跨租户，租户 admin 仅本租户
   - 错误语义：缺少/无效凭证 401 UNAUTHORIZED；角色不足 403 FORBIDDEN；
     显式请求其他租户 403 TENANT_MISMATCH；租户不存在 404
     TENANT_NOT_FOUND；其他租户的文档/会话/任务一律 404。
   - 所有密钥比较使用 secrets.compare_digest；密钥不进入日志、响应或
     管理页面；/admin/tenants 仅返回 tenant_id 与 tenant_name。

3. 隔离实现
   - Mongo：documents/ingestion_tasks/chat_sessions/chat_messages 均含
     tenant_id；查询、更新、删除全部带租户条件；索引以 tenant_id 前缀
     重建，并以 uq_tenant_source 替代旧的 source_path 唯一索引。
   - doc_id = "doc_" + sha1("{tenant_id}:{relative_path}")[:16]，
     同名文件在不同租户下互不覆盖。
   - Milvus：单 collection + tenant_id 字段（INVERTED 索引）；写入必带
     租户，检索/删除/计数强制拼接 tenant_id 过滤；缺少租户参数直接报错。
   - 数据目录：default 租户继续使用 DATA_DIR；其他租户使用
     DATA_DIR/tenants/{tenant_id}/，上传落在其 uploads/ 子目录，
     路径解析校验必须位于租户根目录内。
   - 管理后台：登录后按凭证解析可用租户；全局管理员可切换“全部租户/
     单租户”，租户 admin 仅本租户；切换租户会刷新概览、文档、任务等视图。

4. 迁移脚本（scripts/migrate_multitenant.py）
   - 默认 dry-run，只打印统计；--apply 才写 MongoDB（执行前务必备份）。
   - --apply 回填 tenant_id 为 null/空字符串的文档/任务/会话/消息到
     default，并按 tenant_id+source_path 重算 doc_id。
   - Milvus 租户 schema 不合法时，--apply --recreate-milvus 重建集合
     （删除全部向量，破坏性操作）；schema 已合法时默认跳过，
     需显式 --force-recreate 才会重建；--recreate-milvus 必须配合 --apply。
   - 先探测/修复 Milvus，再写 Mongo；Mongo 侧先 ensure_schema 建新索引，
     最后才删除旧索引，避免应用启动时无索引可用。
   - 迁移后需重新导入：python scripts/ingest_dir.py --tenant default --force。
